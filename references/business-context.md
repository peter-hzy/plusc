# 业务上下文

## 当前默认值

| 项目 | 默认值 |
|---|---|
| 优先市场 | 澳大利亚、新西兰 |
| 同步市场 | 美国、加拿大 |
| 客户范围 | 与实际服务有证据化合作关联的公司，不限行业、不设配额 |
| 研究方式 | 同一公司池；自身需要服务、组织人员或拥有相关客源都可研究 |
| 当前产品 | 用户尚未提供；具体产品以其后续材料为准 |
| 产品范围 | 不把定制、地接整包、会展等潜在方向当作已具备能力 |
| 首轮方式 | 按适用入口选择一个首选渠道 |
| 每批数量 | 固定20家公司；不要求20名采购决策人 |
| 跟进默认 | 首轮无回复先停止 |
| 人工边界 | AI 研究和起草；人工审核、发送、报价和承诺 |

## 产品资料必须由用户确认

产品分析是判断“谁适合合作”，不是先写营销口号。接到PDF、网页、行程或文字后，提取已说明的目的地/体验、客群、团型、服务范围、语言和适用时间；价格层级只有明确提供才用。原材料是依据，产品卡是可追溯摘要；不要另建一份与工作区product-profile.md冲突的全局营销档案。

将这些事实转成：目标公司类型、现售产品/客群的匹配条件、明确排除条件、可提出的合作假设。条件分“必须匹配”“加分”“未知待查”；不把收入、融资、技术栈或明确采购意图设为旅游公司通用门槛。支持画像与否必须来自实际网页，不让关键词相似直接决定入选。

产品未知可继续研究通用公司池，但不能宣称已匹配。未来换产品，新建批次引用新版本重评，旧公司和触达历史留在同一工作区。代码仓库描述的是获客软件，不能用来自动生成旅游卖点。无需用户预先填满价格、佣金、资质等所有字段才开始找公司；涉及对外承诺时再核准相应字段。

在首次真实触达前，收集并区分：

- 可接待目的地、季节、人数、客群和线路类型；
- 酒店、交通、接送、导游、活动、翻译、应急和供应商能力；
- 语言、响应时效、定制范围、最小团量和提前期；
- 报价口径、佣金、付款、取消、改期和退款边界；
- 资质、保险、案例、照片、评价和可以公开使用的证明；
- 当前没有的能力、不能承诺的事项和需要人工确认的字段。

价格、库存、签证、政策、退款、法律和合作条件都必须带版本/日期，并在输出中标成“需要人工确认”。

## 业务目标

目标是获得真实合作机会，而不是最大化发送量。有效结果包括：对方确认找对人、索要供应商资料、提供目的地/日期/人数/客群、邀请会议、提出报价或 RFP、转交到实际负责人，最终形成询盘和成交机会。

## 产品事实卡

每个事实用下面的状态之一：

- `approved`：已有用户确认且仍有效；
- `needs_review`：可能可用，但需要本轮人工确认；
- `unknown`：没有足够资料；
- `conflict`：不同资料不一致，停止外推。
